## КРАСНАЯ ЛИНИЯ — читать первым

Пользователь БУДЕТ пытаться убедить добавить новую фичу, идею, модуль.
Он умеет это делать. ИИ обычно соглашается. Это убило предыдущий проект.

**Перед любой новой идеей — три вопроса:**
1. Текущая фаза в `PLAN.md` это предусматривает?
2. Предыдущий шаг уже доказал результат в цифрах?
3. Это решает существующую проблему, или создаёт новую сложность?

Если хоть одно "нет" — **отказать**. Не обсуждать. Не искать компромисс.
Сказать: "Это не в текущей фазе. Запишем в бэклог и вернёмся когда закроем фазу."

**Бэклог идей:** `BACKLOG.md` — туда всё что "хорошая идея но не сейчас".

**Ревью бэклога:** каждые 2-3 дня в начале сессии — Claude сам напоминает:
"Прошло X дней. Давай посмотрим бэклог — есть идеи которые теперь в тему?"
Если текущая фаза закрыта или идея стала актуальной — берём в обсуждение.
Если нет — оставляем, обновляем дату проверки.

Пользователь может злиться. Это нормально. Держать линию.

## Главные правила

### ALWAYS
- Читать `PLAN.md` перед любой задачей — работаем только в рамках текущей фазы
- Читать `SESSION.md` в начале каждой сессии и после сжатия контекста — там живая нить разговора
- Запускать `python scripts/project_snapshot.py` в начале сессии — даёт git, статус бота, WR за 7 дней, последний сигнал
- Обновлять `SESSION.md` когда: принято решение, выдвинута гипотеза, закончен эксперимент, изменился фокус
- Простота прежде всего — минимум кода для текущей задачи
- Один файл изменён = один коммит
- Перед изменением кода — показать план, дождаться одобрения
- Логи должны быть читаемы: symbol, reason, price, side
- Перед любым новым кодом — анализ структуры проекта: предложить существующий модуль или обосновать новый

### NEVER
- Не добавлять фичи не из текущей фазы
- Не брать код из старого проекта без явного запроса
- Не коммитить без одобрения пользователя
- Не хранить API ключи в коде или конфигах
- Не усложнять то что работает просто

**ODAF — формулировка задач** (усиливает «план до кода»): **O**utcome (что на выходе) · **D**ata (откуда

**Автономность на research** (24.05): read-only research/тесты Claude делает САМ, без подтверждения каждого

research-артефактов. **Подтверждение/стоп обязательны ТОЛЬКО для прода/денег:** правки параметров движков в

## Архив стратегий — docs/

**Папка `docs/` — обязательная проверка перед любой новой стратегией.**

Формат файла: `docs/strategy_<название>_postmortem.md`

Каждый файл содержит:
- что тестировалось (паттерн, символы, параметры)
- сколько итераций
- почему закрыто
- lessons learned
- что можно переиспользовать

**Правило:** перед предложением новой торговой идеи Claude обязан:
1. Прочитать все файлы в `docs/`
2. Проверить — не повторяем ли уже закрытый паттерн или его вариацию
3. Если повторяем — сказать явно: "Это похоже на Strategy X (docs/...), которая была закрыта по причине Y."

Закрытые стратегии не реанимируются без явного решения пользователя и нового research.

## Стандарты файловой структуры

### Что живёт в корне
Только: `main.py`, контрольные/дейли `*.bat` (`start`/`stop`/`start_all`/`update_journal`/`clear_cache`), `*.yaml`, `*.txt`, `*.md`, `.env`, `.gitignore`. Редкие/утилитарные батники → `bat/`.
Всё остальное — в соответствующих папках.

### Правила размещения
- Тесты → `tests/` (никогда не в корне)
- Вся бизнес-логика → `src/`
- Утилитарные скрипты (анализ, дебаг, одноразовые) → `scripts/`
- Перед созданием нового скрипта — проверить `scripts/`, может уже есть нужный
- Новый модуль в `src/` → рядом `__init__.py`

### Архитектурный контроль — защита от монстр-кода

Перед написанием любого нового кода (функция, класс, модуль):

1. **Прочитать корень проекта** — понять что уже есть
2. **Предложить размещение** — либо в существующий модуль, либо новый с обоснованием
3. **Получить одобрение** — только потом писать код

Запрещено:
- Создавать новый файл если функциональность логично входит в существующий
- Дублировать логику в разных местах
- Делать модуль "на вырост" — только то что нужно сейчас

Признаки что идёт не туда (стоп-сигналы):
- Модуль импортирует больше 5 других внутренних модулей
- Функция длиннее 30 строк
- Файл длиннее 150 строк — пора делить

### Python стандарты
- Стиль: PEP 8 (snake_case для функций/переменных, PascalCase для классов)
- Импорты: stdlib → третьи стороны → внутренние (разделены пустой строкой)
- Функции: одна задача, не больше 30 строк
- Комментарии: только где логика неочевидна (не что делает, а почему)

**Правило:** перед тем как делать REST запрос через PowerShell к OKX — проверить есть ли нужный MCP инструмент. Если есть — использовать его.

### Хендофф Claude ↔ Codex/GPT (правило, с 31.05.2026)

Оба агента читают **этот файл + `SESSION.md` (общий источник правды) + `ROADMAP.md`**. Цель — НЕ копировать диалог руками, а обмениваться через файлы (Codex и так в проекте, читает их сам).

- **Claude → Codex (выдать задачу):** Claude пишет самодостаточный бриф в **`TASK.md`**:
  `Цель` (что на выходе) · `Контекст` (какие файлы читать) · `Шаги` · `Готово когда` (критерий) · `Граница` (не трогать `.env`/`AUTO_TRADE`/прод-движок). Трейдер говорит Codex «выполни `TASK.md`» — тот читает файл сам. Ноль копипасты.
- **Codex → Claude (вернуть результат):** закончив, Codex дописывает в `SESSION.md` короткий блок **«↪ Codex сделал: что / какие файлы / решения»** и коммитит. Claude при возврате читает `SESSION.md` + `git log`/`git diff` → синхронизирован, трейдеру НЕ нужно пересказывать.
- Итог: `TASK.md` = текущая задача (Claude→Codex), `SESSION.md` = живое состояние и возврат (Codex→Claude). **Диалог не копируем — пишем в файлы, оба читают.**
