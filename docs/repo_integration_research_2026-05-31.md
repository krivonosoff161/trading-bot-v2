# Repo integration research — 6 кандидатов (31.05.2026)

Цель: не обзор ради обзора, а решение по каждому репо: нужно ли нам сейчас и как встраивать в текущую систему инфо-эджа. Контекст: Main как направленный скальп закрыт/заморожен; текущий вектор — воркфлоу Codex/Claude и keyless-инфо-скауты (`daily_digest_collector.py`, `research_scout_orchestrator.py`, `onchain_whales_probe.py`). Граница: не запускать чужой торговый AI как money-machine, не трогать `.env` / `AUTO_TRADE` / `config.yaml` / прод-движок.

## По каждому репо

### 1. `rohitg00/agentmemory` — NOW

**Почему нужно:** это единственный кандидат, который прямо бьет в текущую боль ROADMAP Фазы 1: контекст между Codex/Claude не должен переноситься копипастой. В отличие от `SESSION.md`, память может искать по прошлым tool-use/решениям и отдавать короткий релевантный контекст, а не весь живой лог.

**Факты:** активный проект, Apache-2.0, релиз `v0.9.24` от 2026-05-29. README заявляет поддержку Claude Code/Codex через MCP/hooks, локальные embeddings, no-op LLM provider по умолчанию и отсутствие внешнего DB как обязательной зависимости.

**Как интегрировать:**
1. Не заменять `SESSION.md`: он остается human-readable source of truth и хендоффом.
2. Поставить `agentmemory` локально в отдельный тестовый контур и подключить только к Codex/Claude Code, если хуки не требуют доступа к `.env`.
3. Включить `AGENT_ID` для ролей `codex`, `claude`, `researcher`, чтобы не смешивать выводы без происхождения.
4. Сначала сохранить 5-10 синтетических хендоффов: "решение", "файл", "вердикт", "запрет". Проверить, что поиск возвращает актуальное, а не старое.
5. Только после этого включать автозахват реальных сессий. Любые секреты и торговые файлы — в denylist.

**Почему не сразу в прод-ритуал:** память опасна тем, что делает старые выводы убедительными. В нашем проекте это уже убивало стратегии; значит обязательны TTL/префикс даты/вердикт "устарело".

### 2. `NousResearch/hermes-agent` — LATER

**Почему не сейчас:** Hermes — это полноценный агентный runtime, а нам сейчас нужен не еще один агент, а накопление OOS-данных по инфо-источникам. Он требует модельного провайдера или локальный LLM, плюс отдельную операционную поверхность: VPS, Telegram gateway, permissions.

**Что полезно:** unattended-режим. Если Scout #1/#2 докажут, что ежедневный digest полезен, Hermes может стать "ночным оператором": cron запускает `research_scout_orchestrator.py`, сохраняет `forward_series.csv`, присылает краткий статус в Telegram и ничего не трогает в торговле.

**Путь интеграции позже:**
1. Поднять в WSL2 или на отдельном дешевом VPS, без OKX ключей и без доступа к `.env`.
2. Рабочая директория только `scripts/analysis/research/` и `docs/`.
3. Разрешенные команды: запуск scout-скриптов, чтение output, отправка Telegram summary.
4. Запрет: `config.yaml`, `start_all`, `AUTO_TRADE`, live trading, git push без явного review.

**Риск:** это удаленный агент с терминалом. До доказанного value от scout-накопителя его эксплуатационная сложность выше пользы.

### 3. `stablyai/orca` — LATER

**Почему не сейчас:** Orca полезен, когда несколько агентов параллельно делают независимые ветки и нужно управлять worktrees/diffs/PR. Сейчас правило хендоффа уже задает более дешевую схему: `TASK.md` туда, `SESSION.md` обратно, git diff/log для синхронизации.

**Что полезно:** если пойдет фаза репутационного repo или несколько параллельных research-проверок, Orca может дать контроль worktree-веток и видимость, что делает каждый агент.

**Путь интеграции позже:**
1. Поставить desktop app без подключения к торговым ключам.
2. Одна задача = один git worktree, один агент.
3. Разрешить Orca только для code/research веток, не для live-бота.
4. Оставить `TASK.md` как входной контракт, чтобы UI не стал заменой дисциплины.

**Риск:** преждевременно добавит "оркестрацию ради оркестрации". До появления настоящей параллельной нагрузки это лишний слой.

### 4. `Fincept-Corporation/FinceptTerminal` — SKIP

**Почему мимо интеграции:** проект живой и функционально широкий, но он тяжелый: C++20/Qt6 desktop terminal, embedded Python, брокеры, real-time trading, AI agents, 100+ data connectors. Для нас это не библиотека, а отдельная платформа, которая дублирует идею монитора и вносит сильный license/commercial risk.

**Факты:** README указывает AGPL-3.0 + коммерческую лицензию и явно требует коммерческую лицензию для business/internal use. Есть платные/опциональные data-провайдеры и брокерские интеграции. Это несовместимо с текущей границей "keyless/без денег по умолчанию".

**Что можно забрать без интеграции кода:** список идей по источникам. Например, сверить наши текущие источники (CoinGecko, RSS, OKX, Fear&Greed, DeFiLlama) с их публичными data connectors и вручную выбрать 1-2 бесплатных источника, если они дают новый сигнал, а не еще один шумовой dashboard.

**Вердикт:** не ставить и не тащить код. Источники можно изучать как reference, но repo как компонент не лезет.

### 5. `cporter202/API-mega-list` — NOW

**Почему нужно:** это дешевый способ расширить Scout #1 источниками, не строя терминал и не покупая данные. В README заявлено 10 498 API в 18 категориях, включая `News`, `MCP Servers`, `Open Source`, `Social Media`, `Data Collection`.

**Ограничение:** у репо нет явной лицензии в GitHub metadata. Значит нельзя копировать крупные куски каталога/таблиц в наш репозиторий как данные. Используем только как навигацию: открыть, выбрать кандидатов, перейти к первоисточнику API, проверить лицензию/лимиты уже там.

**Путь интеграции:**
1. Просеять только категории, полезные для инфо-эджа: `news-apis-590`, `mcp-servers-apis-131`, `open-source-apis-768`, `social-media-apis-3268`.
2. Для каждого кандидата фиксировать: keyless? free tier? RSS/API? rate limits? крипто-релевантность? можно ли OOS-логировать?
3. В Scout #1 добавлять только источники, которые дают структурированные события или заголовки с временем, а не маркетинговую кашу.
4. Каждому новому источнику сразу добавить поле в bundle + honest `sources_failed`, как уже сделано в `daily_digest_collector.py`.

**Первый практичный результат:** shortlist 5-10 источников для `daily_digest_collector.py`, из них внедрять не больше 1-2 за раз и смотреть, улучшает ли это ручной/LLM digest.

### 6. `anthropics/financial-services` — LATER

**Почему не сейчас:** это не crypto-info scout, а reference-набор финансовых Claude agents/skills/connectors для investment banking, equity research, PE, wealth, fund admin. Многие MCP-коннекторы — Daloopa, Morningstar, S&P, FactSet, Moody's, LSEG, PitchBook и т.д. — требуют подписку/API key.

**Что полезно:** структура. Репо хорошо показывает, как упаковывать финансовые workflows в plugins/skills/commands, как держать human sign-off и как отделять agents от connectors. Это пригодится для Фазы 3 "репутация" и для будущего analyst workflow, но не для текущего keyless накопителя.

**Путь интеграции позже:**
1. Изучить структуру `plugins/vertical-plugins/*/skills` и `commands`, не ставя платные MCP-коннекторы.
2. Сделать наш легкий аналог: `research-methodology`, `strategy-postmortem`, `data-source-audit`, `oos-checklist`.
3. Для любых managed agents оставить жесткий human sign-off: агент пишет отчет, не торгует и не меняет прод.

**Вердикт:** учиться у packaging, не подключать runtime.

## Что брать первым

1. **`agentmemory` первым** — потому что напрямую закрывает боль хендоффа Codex/Claude из ROADMAP Фазы 1. Но только как пилот поверх `SESSION.md`, не вместо него.
2. **`API-mega-list` вторым** — потому что это дешевый вход в расширение Scout #1. Это не runtime dependency, а источник кандидатов на новые keyless feeds.
3. **Hermes позже** — только когда есть доказанный полезный daily scout и нужно unattended-исполнение.

`FinceptTerminal` не брать как компонент из-за лицензии/тяжести/дублирования. `Orca` отложить до настоящей параллельной агентной нагрузки. `anthropics/financial-services` отложить как учебник по packaging и financial-agent discipline, не как источник торгового эджа.
